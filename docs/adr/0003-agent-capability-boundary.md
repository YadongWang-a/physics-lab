# agent 能力边界：只用 Pi agent 内建能力 + 原样 skill，不写扩展

桌面应用的所有 agent 功能必须通过集成 Pi agent（`@earendil-works/pi-coding-agent`）实现：不自行实现 LLM 调用/agent 循环；自定义工具与扩展数量最小化；physics-lab-skill 直接调用（默认加载、常驻），不对 skill 内容做任何修改。

**Status**: accepted

**Considered Options**:
- 自建 LLM 调用层 —— 灵活但重复造轮子、失去 skill/会话/事件流生态
- 大量自定义工具/扩展（如独立运行时检查工具）—— 功能强但违背"尽量少"约束
- 修改 skill 适配应用 —— 用户明确禁止（skill 是资产，应用适配 skill 而非相反）

**Consequences**:
- 工具面 = Pi 内建工具的最小够用集（write/edit/read 等），自检依赖 skill 原样流程
- skill 以只读方式随应用打包（`resources/`），运行时不可变
- 若未来需要超出内建能力的工具，须重新评估约束（记录于本 ADR 的修订）

## 修订（2026-09-29）：read 的大文件拦截

实测一次真实生成（`app-20260929.log`）：模型整读 `lib/common.js`（80KB）后又反复 grep 它，该文件共 10 次工具往返、占该回合 35 次工具调用的约 40%，并把 80KB 常驻上下文拖慢其后每一轮（单回合 13 分钟）。提示词里的「不整读 lib/common.js」是软约束，已被违反。

据此在工具面加一个**同名覆盖**的自定义 `read`（`src/main/agent/guarded-read.ts`，以 SDK 的 `createReadToolDefinition` 为基座）：`lib/` 下超过 64KB 的文件**整读**时返回提示并放行**定向读**（`offset + limit ≤ 60`），grep 与未超限的小文件不受影响；read 的工具描述也提前声明该规则。它是对既有内建工具的**收窄**包装、不新增能力面，故不视为对本 ADR「最小工具面」的突破。

实测补记（同日一次真实生成，问题为"斜面物块下滑 + v-t 图"）：拦截生效（无整读），但该回合工具调用 35 次、其中 `common.js` 命中 **21 次**（基线 10 次）、grep 22 次——**整读被 grep 风暴替代，轮次未下降**。原因推断为拦截文案把模型引向 grep；已改为"给合法通道"（定向读 + 工具描述前置声明）。

第二次实测（同日 15:02，半球手倒立题，10.1 min / 43 次工具调用 / 44 轮）：**23 次（53%）仍在刨 lib 源码**（14 次分段 `read common.js` + 5 次 grep + 6 次 common.css），而模型**一次都没调 `check_demo`**——它手里有能在沙箱真跑页面的验证工具，却用读源码来"确认行为"。每轮约 14 s、工具自身执行仅 4.1 s，说明耗时几乎全由轮数 × 通道延迟决定。

据此把策略从"给读源码的通道"改为**给验证的通道**：提示词 §7 与 read 守卫文案都改为「助手行为或时序拿不准时, 调 `check_demo` 拿沙箱实测」，不再引导 grep/分段读。定向读（`offset+limit≤60`）仍放行作为兜底。

第三次实测（同日 15:16，A/B，同题 42 轮）：**规则被完全忽略**——`check_demo` 调用仍为 0，lib 源码探测 27 次（64%）。机械原因：守卫文案只在"整读被拦"时出现，而模型学会了每次都带 `offset+limit` 绕开拦截，**从未读到那句新规则**。结论：守卫文案与提示词"劝"都打不过"读源码确认"的习惯。

因此收口为**硬墙 + 替代品**（本轮最终形态）：

- `read`：`lib/*.js` 一律拦截（不分大小、不给 `limit` 口子——分段读同样是一次往返，且会被用来替代验证）；`lib/` 下其它 >64KB 文件的定向读仍放行。
- `grep`：检索 `lib/*.js` 或整个 `lib` 目录被拦截（新增 `guarded-grep.ts`，与 read 同策略：被拦后会改用反复 grep，同样是一轮往返）。
- 替代品：seed lib 时从 `common.js` 自动生成 `lib/INDEX.md`（88 条：助手名 + 签名 + 紧邻注释，7.5KB，每次 seed 刷新不漂移）；参数细节仍在 `drawing.md` §4/§5；**行为/时序问题用 `check_demo` 在沙箱真跑页面确认**。
- 配套：§7 改为**分段落地**（可运行的最简页 → seg → hud/矢量 → 图表，每段后跑一次 `check_demo`），见 ADR-0007——"早写=早可跑=验证变便宜"是让模型不必读源码的正面出口。

## 修订（2026-10-05）：工作目录演示名单注入 system prompt（消掉 `ls` 探索）

创建会话时把工作目录根下的 `*.html` 名单扫出来，注入 system prompt 的「工作目录现有演示」一节（`agent-runner.skillSystemPrompt(skillDir, existingDemos)`，`session-host.getSession` 计算）。命名查重以这份名单为准：重名换名、不询问、不列目录。

**证据**（同题一次真实生成，`_new-1791188210058-2kwqsi`）：模型在写文件**之前**先发了一轮 `ls(.)` 查重名（提示词原本要求「重名先问用户」），那一轮 **95.7s / 22,841 推理令牌**，占整次 643s 的 15%——工具本身只花 90ms，成本全在模型的思考与往返上。

**Considered Options**:
- **保持「重名先问用户」** —— 否决：它必然导致一次列目录；且与「不问用户」的总方向冲突
- **应用层替模型定文件名** —— 否决：命名要带物理语义（kebab-case + `-3d` 后缀），是模型的判断
- **只删「重名先问用户」不给名单** —— 否决：模型会更盲目地猜，撞名风险更高

**Consequences**:
- 名单在**创建会话时**扫描一次：会话内新建的演示由模型自己写，无需再查；跨会话期间新产生的文件不在名单里——撞名的兜底是 `write` 覆盖，故名单以「尽量避免」而非「强保证」表述；名字冲突代价低（换名即可）
- `skillSystemPrompt` 新增第二参数（缺省空数组，既有调用不受影响）；`test/agent-skill.test.ts` 增加注入契约

## 修订（2026-10-07）：新增 `read_image`——题图回看通道（工具面 +1 的评估）

**必须新增的原因（保真缺口）**：extract 路上视觉转述是**一次性**的，主模型看不到原图（实测：进入会话的用户消息 437 字里 415 字是转述，会话里 `image` 块 **0** 个）。没有回看通道时，转述里标着不确定或自相矛盾的几何只能靠猜——第 15 题实测转述同时给出「I 区磁场垂直纸面向外」与图上标注「×」，主模型在隐藏思考里反复猜（原话 `I区磁场垂直纸面向外，标注"×" — contradictory but let's take:`）。

**为什么这不是"重复造工具"**：内建工具里没有任何"看图"能力——`read` 只读文本（且 `lib/*.js` 被拦截），视觉模型的调用权原本只在应用层（`extractImageText`）。所以这是**能力缺口**，不是既有能力的封装；本 ADR 的"工具面最小化"要求重新评估，故记此修订。

**边界（收窄到最小能力）**：
- 只能回看 `<工作目录>/.pi-sessions/attachments/` 内的图片：`resolveAttachment` 拦掉越界路径（含 `../`）、不存在的文件、非图片扩展名——它不得变成"拿图片当借口读任意文件"的通道。
- 题图在每个回合落盘一次（`saveChatImages`，会话附件，随工作目录迁移，ADR-0002）；注入文本把附件路径交给 agent，并说明"先用 `read_image` 就那一点定向追问，仍不清再问用户"。
- 一次只问一件事（工具描述里写明"重述整张图请勿用它"）；视觉槽位未配置时工具返回明确文案，不静默失败。
- 提示词 §2 增「转述不确定处回看原图」。

**代价**：常驻多一条工具描述（token）；每次回看是一次额外的视觉模型调用（只在模型判断需要时发生）。

**Consequences**:
- `test/read-image.test.ts`（附件边界：越界/不存在/非图片三种拒绝）与 `test/image-attachments.test.ts`（落盘扩展名与字节保真、会话键不逃逸目录）
- 视觉槽位由 `getVisionSlot` 每次读取（设置改后新会话即生效）；未配置时不注册该工具
