# 物理演示生成桌面应用（Physics Lab Desktop）

Status: ready-for-agent
Feature: physics-lab-desktop-app
Created: 2026-08-18

## Problem Statement

中学物理老师想用一道物理题（文字或照片）快速生成可课堂演示的交互式 HTML 演示，并能在对话中反复修改。现有 physics-lab-skill 已能生成高质量的演示 HTML，但它运行在终端里，老师无法使用：没有界面、看不到生成结果、无法对话式修改。老师需要的是一台 Windows 桌面应用：左边和 AI 对话，右边实时预览生成的演示，一个演示对应一段独立的对话（会话），成果是一个可以拷贝到任何电脑、用浏览器直接打开的文件夹。

## Solution

一个 Windows 桌面应用。老师启动时指定一个工作目录，此后所有演示 HTML、共享资源、对话历史都放在该目录里 —— 拷贝整个目录即可在任何电脑的浏览器中打开所有演示。界面左侧是聊天窗口（流式输出、可贴题目照片、可随时停止），右侧是生成演示的实时预览（文件一变自动刷新），支持全屏演示模式直接投屏上课。每次生成由 agent 严格按照 physics-lab-skill 的完整流程执行：判定输入类型（题目/物理过程）、必要时澄清几何、索要并核对答案、先推导再生成、模板填空、程序化自检、失败自动修复。模型与图片理解能力由老师自带 API Key 提供：一个主模型 Key（默认纯文本模型如 DeepSeek）+ 一个可选的视觉模型 Key；配置了视觉模型时，照片先由视觉模型读取内容，再由主模型完成生成工作。

## User Stories

1. 作为老师，我启动应用时指定自己的工作目录，这样所有演示都集中在我熟悉的位置，拷贝目录即可带走全部成果
2. 作为老师，我再次启动应用时它记住上次的工作目录，这样我不必每次重新选择
3. 作为老师，我输入一道物理题的文字描述，就能得到一个可交互的演示 HTML，用于课堂讲解
4. 作为老师，我描述一个物理过程（如"绳环从高处下落"）而不带设问，agent 也能生成演示，不需要我提供答案
5. 作为老师，我贴一张题目照片，应用能自动读取图片内容并据此生成演示，这样纸面习题也能直接用
6. 作为老师，我配置了视觉模型而主模型不支持图片时，照片自动经视觉模型转成文字再进入对话，我无需关心内部处理
7. 作为老师，我只配置了一个不支持图片的模型 Key 时，应用明确提示"当前无法识别图片"，而不是静默失败
8. 作为老师，生成过程中几何信息含糊时（如谁在上谁在下），agent 一次一个问题地问我，确保装置画对
9. 作为老师，我输入的是带答案的题时，agent 先请我提供答案/解析并据此核对，避免整版返工
10. 作为老师，agent 在生成前把假设清单和完整推导过程展示给我，这样我能发现模型级错误并及时纠正
11. 作为老师，agent 生成的每个演示都以英文文件名存放、界面以中文标题展示，这样文件名安全且我能认出内容
12. 作为老师，文件名与已有文件冲突时，agent 先问我改名还是覆盖，不擅自覆盖我的文件
13. 作为老师，我的每次修改要求都在同一段对话里生效（"把摩擦系数改成 0.2"），演示随之更新
14. 作为老师，我关掉应用再打开，之前的对话和演示都还在，我可以继续上次的修改
15. 作为老师，agent 每次生成后自动自检（语法、元素引用、运行时错误、画布渲染、物理一致性），不把坏文件交给我
16. 作为老师，自检发现问题时 agent 自动修复并重跑检查，不需要我介入
17. 作为老师，修复循环进行时我能看到检查结果和修复过程，而不是黑盒等待
18. 作为老师，任何时刻我都能点"停止"打断 agent，防止它无休止地工作
19. 作为老师，生成完成后右侧预览立即展示最新演示，文件变化自动刷新
20. 作为老师，我可以点击"演示"进入全屏演示模式，直接投影到教室屏幕上上课
21. 作为老师，演示模式下键盘操作（空格暂停/继续、重置）照常可用，方便课堂节奏控制
22. 作为老师，同一道题想要 2D 和 3D 两个演示时，它们作为两个独立演示并存，各自有独立对话
23. 作为老师，我可以在工作目录里看到所有演示的列表（中文标题），点击切换预览和对话
24. 作为老师，我删除一个演示时应用二次确认，避免误删我的成果
25. 作为老师，我把工作目录拷到另一台电脑并指定为工作目录，演示和对话都能继续使用
26. 作为老师，我把单个演示 HTML 发给同事时，它（连同 lib 资源）双击即可在浏览器离线运行
27. 作为老师，我在设置页配置模型供应商、模型名和 API Key，应用加密保存，不会明文泄露
28. 作为老师，我可以额外配置一个自定义 OpenAI 兼容的视觉模型端点，用于图片理解
29. 作为老师，生成质量有问题时我直接说"重做/改这里"，agent 按 skill 流程重新推导或局部修改
30. 作为老师，我输入非物理内容时 agent 明确拒绝并说明原因，不会乱生成

## Implementation Decisions

- **技术栈**：Electron + React（electron-vite 三端构建）；agent 能力通过 Pi SDK（`@earendil-works/pi-coding-agent`）进程内嵌入，不引入额外 sidecar 进程
- **agent 能力边界**（ADR-0003）：所有 agent 功能通过 Pi agent 实现，不自行实现 LLM 调用；自定义工具与扩展数量最小化；不对 skill 做任何修改
- **工作目录所有权**（ADR-0001）：所有演示产物、资源、会话历史存于用户指定的工作目录；应用只读写不擅自删除用户文件，删除需二次确认
- **工作区布局**（ADR-0002）：演示 HTML 平铺于工作目录，共享一份 `lib/`（common.css/common.js/mathjax.js）；会话不依赖 Pi 按 cwd 的默认分组，每个演示 HTML 对应 `.pi-sessions/` 下一个独立 session 文件
- **演示清单契约**：`.pi-sessions/demos.json` 维护 文件名称 ↔ session 文件 ↔ 中文标题 ↔ 创建时间 的映射，用于文档列表展示与会话恢复；跨机器迁移容忍 cwd 路径变化
- **skill 即默认行为，只读打包**：物理演示生成不设"引入"概念 —— physics-lab-skill 的指令常驻于系统提示，agent 始终完全按其 7 步流程执行（判定输入 → 澄清几何 → 推导与答案确认 → 命名 → 拷贝 lib → 模板填空 → 自检）；skill 内容（SKILL.md/drawing.md/模板/lib）随应用以只读方式打包（`resources/`），运行时不可变、不修改任何内容；`drawing.md` 与 2D/3D 模板按 skill 原设计按需读取
- **交互澄清**：全量保留 skill 的澄清机制 —— 几何/位置关系含糊时一次一问；是"题目"且无答案时先索要答案/解析；"物理过程"则简述理解即可
- **工具集**：仅启用 Pi 内建 `read, write, edit, grep, find, ls`（禁 `bash`），外加**唯一一个自定义工具** `check_demo`（规避 Windows 无 bash 的运行时依赖；其语法编译检查取代 skill 原流程中的 `node --check`）
- **check_demo 自检工具**：agent 的唯一自定义工具，返回结构化 `{ok, issues[]}`；含静态检查（末段 script 语法编译、`$('id')` ↔ `id` 交叉核对、骨架标记断言）与运行时断言（沙箱 webview 加载、console 错误捕获、状态无 NaN/发散、画布像素采样、agent 可传入的自定义断言片段如能量守恒漂移）；失败自动修复重跑，不设上限，聊天区"停止"按钮为兜底控制
- **预览与检查共用一个沙箱 webview**（sandbox + contextIsolation + 禁 nodeIntegration）；`fs.watch` 监听文档变化自动刷新；演示模式 = 全屏渲染当前演示
- **OCR 通道**：双槽位 Key（主模型 + 视觉模型，各自可独立配置，也可同 Key）；主模型支持视觉 → 图片 base64 直通会话；主模型不支持视觉且配置了视觉模型 → 图片先经视觉模型提取文本/公式再进入会话；仅单 Key 且不支持视觉 → 图片输入不可用并明确提示
- **密钥存储**：Electron safeStorage（Windows DPAPI）加密存储 API Key；模型运行时认证文件置于应用私有目录，不写入全局 `~/.pi/`
- **模型配置**：支持 Pi 原生供应商列表 + 自定义 OpenAI 兼容端点（baseURL + 模型名 + Key），主模型与视觉模型各自独立；模型列表动态获取
- **命名**：生成的 HTML 用 kebab 英文文件名（skill 约定），中文标题经清单映射展示
- **分发**：electron-builder NSIS 安装包；不做自动更新、不做代码签名（v1）

## Testing Decisions

- **测试 seam（用户选定）**：Pi SDK 调用层 —— 主进程中直接使用 `createAgentSession`/会话管理/自定义工具的那一层；不引入 UI 与 agent 之间的抽象模块
- **好测试的标准**：只断言外部可观察行为（HTML 文件生成、check_demo 通过、事件流顺序与内容、会话可恢复），不测内部实现细节
- **单元测试**：check_demo 的静态检查纯函数（script 语法编译、ID 交叉核对、骨架标记断言）在无 Electron、无 Key 环境下直接测试
- **集成测试（需真实 Key，环境变量门控，不在 CI 默认运行）**：在 SDK 层用样本题目集（覆盖"题目+答案"、"题目无答案"、"物理过程"、"附图"各至少一例）跑完整生成 → 断言演示 HTML 生成、`check_demo` 通过、事件流完整、会话可恢复
- **手动冒烟**：UI 全流程（指定工作目录 → 对话生成 → 预览刷新 → 演示模式 → 设置 Key → 贴图 OCR），发布前人工执行
- **先例**：仓库尚无测试基础设施，本 spec 确立首批测试；测试框架与脚手架在实现阶段选定

## Out of Scope

- 自动更新、代码签名（仅 NSIS 安装包）
- 统一账号/内置 Key/计费体系（老师自带 Key）
- 本地离线 OCR（PaddleOCR/tesseract.js）—— 数学符号识别质量不足，留作远期
- 导出 GIF/视频、嵌入 PPT 的适配
- 多用户/协作/云端同步
- macOS/Linux 支持（v1 仅 Windows）
- 对现有 9 个回归 demo 的内容修改（仅作为参考样例保留）

## Further Notes

- **Windows bash 依赖**：通过禁 `bash` 工具 + check_demo 内置语法编译检查规避（取代 skill 原流程的 `node --check`，能力等价）；若未来 skill 流程需要执行脚本，再评估捆绑 Git for Windows
- **体积**：mathjax.js 约 2.1MB，随工作目录共享一份；每个演示 HTML 引用同目录 `lib/`
- **P0 验证**：技术验证阶段需要至少一个 DeepSeek API Key（本地环境变量，不进代码）
- **修复循环不设上限**：遵循 skill 第 7 步"失败→修复→重跑"；停止按钮与页面级中止为防失控兜底
- **术语**：本 spec 使用 `CONTEXT.md` 词汇（工作目录/演示文档/演示模式/会话/主模型/视觉模型/OCR 通道/题目/物理过程）；与 ADR-0001、ADR-0002、ADR-0003 一致
